# Подключаемые источники файлов: проектное предложение

Дата проверки документации: 18 октября 2026 года. Основание: CHG-026 общего реестра. Статус: только проработка, без реализации адаптеров, подключения аккаунтов, получения ключей или изменения существующего хранения.

## Предлагаемое решение

Оставить mounted folders простым первым вариантом и добавить единый слой источников. Для облаков начать с отдельного rclone-коннектора, S3 предусмотреть также как нативный адаптер, файлы устройства принимать через загрузку из браузера. Перед обработкой облачный объект полностью материализуется в локальный управляемый каталог: FFmpeg, CUE и запись тегов получают обычный проверенный файл. FUSE и привилегированный Docker не требуются по умолчанию.

Это архитектурное предложение. Оно не отменяет действующий контракт защиты оригиналов и безопасной записи. Обратная запись в удаленный источник требует отдельной политики, проверки версии и приемки; по умолчанию результат публикуется отдельно. Тестовая работа с копией текущей коллекции не должна определять названия и устройство всего пользовательского интерфейса.

## Варианты

| Источник | Предлагаемый доступ | Преимущества | Что требуется учесть |
| --- | --- | --- | --- |
| Папка на Docker-хосте | Явно выбранный bind mount | Минимум зависимостей, быстрый scan и произвольный seek | Контейнер видит только смонтированный путь; проверка прав, ссылок и раздельных назначений |
| SMB/NFS, другой NAS | Mount на хосте; в контейнер передать отдельную папку | Совместимость с существующим файловым хранением | Потеря сети, зависший mount, права UID/GID; неполный scan не считать удалением всей коллекции |
| SFTP | rclone или отдельный SFTP-адаптер | Работа с удаленным сервером без общего mount | Проверка host key, ограниченный ключ/корень, потоковая загрузка и проверка изменений |
| WebDAV/Nextcloud | rclone или нативный WebDAV | Один протокол для нескольких систем | Реальные возможности сервера, etag/mtime и надежность докачки проверяются пилотом |
| Google Drive | Сначала rclone; затем нативный OAuth/Picker при необходимости | Выбор файлов/папок, идентификация объектов по ID | OAuth scopes, собственный client ID, квоты, одинаковые имена и shared drives |
| Яндекс Диск | REST/OAuth или rclone | Официальный файловый API | Обновление доступа, пагинация, квоты и временные URL скачивания |
| Облако Mail.ru | Опциональный rclone-коннектор после отдельного пилота | Поддержка сервиса без собственного неофициального SDK | Требования к паролю приложения и слишком широким правам, ограничения загрузок |
| S3-совместимое хранилище | Нативный S3 или rclone | Bucket/prefix, версии, диапазоны, multipart | IAM по prefix, варианты endpoint, цена запросов/egress, холодные классы, версии и checksums |
| Папка ноутбука/телефона | Выбор файлов/каталога в браузере и возобновляемая загрузка | Не нужно монтировать устройство на сервере | Работа браузера, повторное разрешение доступа, ограничения мобильной ОС; это импорт, а не постоянное фоновое подключение |
| Постоянная папка устройства | Необязательный локальный агент на следующем этапе | Автоподхват изменений при закрытом браузере | Отдельная установка/обновление, pairing, ограниченный корень и отзыв доступа |
| OneDrive/Dropbox и другие | Последующие профили общего коннектора | Расширение покрытия без переписывания ядра | Отдельная приемка каждого backend и условий доступа |

Google различает доступ `drive.file` к выбранным/переданным приложению файлам и широкий `drive.readonly`. Выбор папки в UI не превращает широкий scope в техническое ограничение только этой папкой. Состав прав и применимые требования проверки OAuth выбираются при реализации, а не предполагаются одинаковыми для всех установок. [Google Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth). Для rclone предпочтителен собственный OAuth client ID согласно его руководству. [rclone Drive](https://rclone.org/drive/).

Яндекс предоставляет отдельный REST API Диска; это позволяет впоследствии заменить общий коннектор нативным, сохранив контракт источника. Наличие API не подтверждает работу конкретного аккаунта, тарифа и сети. [Яндекс Диск REST](https://yandex.com/dev/disk/rest/?lang=ru-RU).

В текущем руководстве rclone для Mail.ru указан пароль приложения; обычный пароль не подходит. Там же описана проблема, требующая прав на почту, облако и календарь вместо одного облака. Такой доступ нельзя выдавать автоматически ради музыки. Предпочтительны импорт или уже синхронизированная папка, если владелец не принимает эти условия; аккаунт пока не проверен. [rclone Mail.ru](https://rclone.org/mailru/).

## Локальная папка устройства

В UI следует разделить два действия: «Импортировать файлы» и «Подключить постоянный источник». Браузер может передать только явно выбранные пользователем файлы. `showDirectoryPicker()` имеет ограниченную совместимость и требует secure context; установка PWA сама по себе не дает приложению произвольный доступ ко всему диску или постоянную фоновую синхронизацию. Нужен обычный file-picker как запасной путь. [MDN showDirectoryPicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker).

Для большой папки предлагается загрузка по частям с сохранением относительных путей, проверкой размера/хеша, квотой и возобновлением после разрыва. Сервер хранит завершенные части; после закрытия браузера он может завершать уже полученные задачи, но не читать оставшиеся локальные файлы. В качестве транспорта стоит оценить tus; его возобновление не решает автоматически права доступа и повторную доступность файлов устройства. [Протокол tus](https://tus.io/protocols/resumable-upload).

Постоянный агент - отдельная последующая функция: исходящие соединения, явный каталог, pairing с единственным owner, отзыв разрешения, собственное обновление и журнал. Разрабатывать его до проверки спроса не предлагается.

## Контракт источника и обработка

Источник имеет устойчивый `source_id`, тип, имя, выбранный корень, режим чтения/публикации, лимиты и состояние доступа. Объект хранится как `source_id + object_id + version`; полный SHA-256 содержимого считается отдельно. Имя файла не является глобальным ID. Отсутствующий checksum провайдера не заменяется предположением, а ETag S3 нельзя всегда считать MD5 целого файла, в частности при multipart. [Проверка целостности S3](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html).

Предлагаемый интерфейс адаптера: проверка доступа, постраничный list/stat, загрузка с докачкой, получение доступных version/checksum, чтение квоты и явный список поддерживаемых возможностей. Публикация и условная замена объектов - отдельные операции, доступные только поддерживающим их адаптерам. Нельзя обещать POSIX-атомарность любому облачному объекту.

Поток работы: обнаружение -> резерв места -> скачивание во временный файл -> проверка завершенности/хеша/версии -> атомарное принятие в локальный каталог -> обычный аудит/распознавание/редактор -> отдельная публикация. Если удаленный объект изменился во время получения, задача повторяется для новой версии; старая обработка не применяется к новому объекту. Кеш ограничивается размером и сроком, используемые задачи и необходимые версии отката не удаляются сборщиком.

CUE, аудио-образы, `.lrc`, обложки и `.info.json` импортируются как связанный набор с относительными путями. Несколько FILE разрешаются только внутри разрешенного корня. Совпадения имен, регистр и Unicode не должны незаметно объединять разные объекты; недостающие зависимости показываются до обработки. Частичный листинг/отказ доступа не превращается в массовое удаление каталога. Удаления в облаке и на телефоне по умолчанию не распространяются на другие назначения.

## Docker и интерфейс

Предлагается отдельный непривилегированный connector-контейнер рядом с приложением и worker, с ограниченными CPU/RAM/сетью и выделенным staging. Ключи и refresh tokens находятся только на сервере в защищенном хранилище/secret-файлах, не в образе, URL, stdout или обычном экспортируемом конфиге. Для rclone включается узкий внутренний broker операций; его RC API не публикуется наружу. RC умеет гораздо больше чтения музыки, поэтому доступ к произвольным remotes/путям/командам приложению не передается. [rclone RC](https://rclone.org/rc/).

Мастер подключения: тип -> доступ -> выбор корня -> проверка чтения/квоты -> предварительный состав и объем локального staging -> подтверждение добавления. Карточка источника показывает доступность, последнюю полную проверку, квоту, прогресс передачи и причину блокировки. Пауза источника не удаляет уже полученные результаты. Отдельные настройки определяют, откуда читаем и куда публикуем.

Произвольный URL не становится файловым источником автоматически. Для выбранных протоколов проверяются назначение, TLS/host key, перенаправления и разрешенный корень; FFmpeg не получает непроверенную ссылку непосредственно. ZIP-импорт, если понадобится, требует отдельной ограниченной распаковки, а не скрытого обхода той же проверки.

## Предлагаемый порядок и приемка

1. Сохранить mounted folders; добавить возобновляемый импорт файлов/каталога устройства и общий контракт источника.
2. Проверить rclone-коннектор на Google Drive, Яндекс Диске, SFTP/WebDAV; S3 проверить отдельно с реальным version/checksum и оценкой стоимости.
3. Облако Mail.ru принимать отдельным пилотом после проверки прав; OneDrive/Dropbox - по потребности. Нативные облачные адаптеры добавлять при подтвержденной пользе для UI или надежности.
4. Постоянный агент устройства и обратную запись в облачный оригинал рассматривать отдельными согласуемыми расширениями.

Приемочные сценарии до включения каждого адаптера: истекший доступ, отказ сервиса, докачка большого файла, смена версии во время передачи, нехватка staging, повтор после рестарта, CUE с несколькими FILE, Unicode/коллизии имен, частичный scan, отключение источника, отсутствие секретов в логах и запрет выхода за разрешенный корень. Для телефона проверить фактический picker и повторный доступ после закрытия браузера. Документация провайдера не заменяет эти проверки.

Все варианты и порядок выше являются предложением. Реализация и выдача прав новым сервисам остаются отложенными по CHG-026.
