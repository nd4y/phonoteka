# Дополнительные файлы Music Ready

PUB-08 / AC-81 реализованы отдельным opt-in маршрутом. По умолчанию `cover` и `lrc` выключены. План не изменяет аудио, original или work: сначала обычным путем публикуется текущая принятая ревизия аудио в Ready, затем владелец явно готовит и подтверждает дополнительные файлы.

## Интерфейс и API

- `SidecarPublicationPanel` принимает явные `ids`, `disabled` и необязательный `onQueued(jobId)`. Панель встраивается рядом с публикацией выбранных треков. Показывает состав, add/replace/unchanged, хеши, владельцев, подтвержденные объекты и причину неполного результата.
- `POST /api/publication/sidecars/plans`: `{track_ids: [...], cover: false, lrc: false}`, максимум 200 уникальных IDs. Отсутствие обоих флагов отклоняется. Создание плана еще не пишет в Ready.
- `GET /api/publication/sidecars` и `GET /api/publication/sidecars/plans/{id}`: сохраненные планы и детали. Доступ только owner session; изменяющие запросы требуют CSRF.
- `POST /api/jobs`: `{kind: "publish_sidecars", track_ids: [...], params: {plan_id: "..."}}` с `Idempotency-Key`. Состав обязан точно совпасть с планом. Повтор после ошибки получает новый ключ и новую авторизацию владельца, повтор неизвестного результата HTTP использует прежний ключ.
- Префикс `/api/v1` поддерживается общим middleware. Integration token не создает такие планы и не запускает sidecar-публикацию.

## Замороженный состав и общее владение

План содержит SHA-256 work и уже опубликованного Ready, относительные пути, принятый профиль и версию проверки, source provenance, все planned object paths/hashes/sizes/owners, прежние записи реестра и общий `plan_sha256`. Исходные слова и изображения в plan/settings дополнительно не копируются: байты детерминированно читаются из зафиксированной work-ревизии.

`cover.jpg` берется из встроенной front cover. JPEG сохраняется побайтно; PNG явно преобразуется профилем `jpeg_white_q95_444_v1`: белый фон для alpha, JPEG quality95/4:4:4. MIME и декодирование проверяются существующим media-контрактом. LRC берется из встроенного синхронизированного текста, нормализуется в UTF-8 с нулевым offset; частичный текст не превращается в полный. Нет побочных обращений к провайдерам.

Несколько треков одной папки могут иметь один `cover.jpg` только при одинаковом выходном hash. Изменение общего изображения требует включить всех зарегистрированных владельцев в новый план. Удаление owner references и объектов не выполняется. LRC разных аудиофайлов не делит один путь. Уже существующий незарегистрированный sidecar не присваивается автоматически, даже если его байты совпадают с ожидаемыми: требуется внешняя сверка владельцем, защищенные данные не перезаписываются.

До первого нового эффекта проверяется весь состав: фактические work/Ready хеши, принятые профили, действующие разрешения источников, registry CAS, ожидаемые sidecar hashes, коллизии всех целевых путей. В переносимых ключах применяется Unicode NFC + casefold; запрещены управляющие символы, Windows device names/недопустимые символы, завершающие точки/пробелы, file-vs-directory conflicts и разные написания общего каталога. Имена не переименовываются скрытно. Проверка реального Ready namespace ограничена 100000 путей и при превышении останавливается до записи.

Перед каждым отдельным эффектом повторно сверяются DB/gate всего состава, policy/registry и фактическое аудио владельцев этого объекта; по завершении снова хешируется весь состав. Это позволяет не перечитывать всю фонотеку квадратично. Контролируемые writer jobs работают последовательно в обычной scheduler lane под существующим storage writer guard. Внешний SMB-доступ к Ready остается RO; CAS не является межпроцессным протоколом для стороннего писателя.

## Частичность, восстановление, экспорт

Каждый sidecar использует тот же staging на filesystem публикации, fsync, no-replace/expected-hash CAS, backup и recovery journal, что и одиночное аудио. Бюджет backup учитывает размер прежнего объекта. Права нового sidecar наследуются от принятого work-аудио, при замене сохраняются права прежнего sidecar.

Группа не объявляется атомарной. Подтвержденные объекты отражаются отдельно в plan и registry. Ошибка после первого эффекта оставляет `partial`/`interrupted`, задачу `completed_with_errors`/`needs_review` и видимую причину. При рестарте незавершенный план требует нового запуска владельцем; новые эффекты не проигрываются автоматически. Такой повтор сначала сверяет существующие media journals. Совпадение хеша без подтверждающего журнала не принимается за наш commit. Неоднозначные/чужие журналы и внешняя правка назначения дают конфликт.

Новый экспорт блокируется при неполном связанном плане, неподтвержденном объекте или устаревшем owner audio/gate после новой публикации/Ready rollback. Нужен завершенный новый план либо явное продолжение прежнего. Registry не удаляет чужие owner references при этих изменениях. Старый неизменяемый экспорт сохраняет прежние версии.

Manifest и `files/` нового экспорта содержат аудио и все связанные подтвержденные sidecars с paths/hashes/kind/owners/provenance. M3U8 ссылается только на проверенное аудио и создается после копирования и проверки всех объектов поколения. Права известного источника общих байтов сохраняются даже при выборе другого preferred audio owner. Все объекты включены в SHA-256 receipt и защищены тем же export lease/retention. Публикация каждого файла и согласованный неизменяемый export поколения различаются явно.

## Доказательства и пределы проверки

`tests/test_publication_sidecars.py` использует сгенерированные короткие FLAC, настоящий JPEG/LRC и tempFS: opt-in/auth/worker flow, конкурентно подготовленные несовместимые общие cover, регистр/NFC/каталоги, partial после опубликованного аудио и cover, fresh retry, restart между durable journal и registry, отсутствие ложного успеха без журнала, immutable snapshot всех объектов, delivery checksum completeness, stale review и сохранение ограниченного источника исключенного owner, reservation большого старого backup.

При реализации локально выполнены только AST parse и `git diff --check`. pytest, frontend build, браузерная проверка и fault/runtime приемка выполняются на build-01. Этот документ не утверждает результат еще не выполненного прогона и не заменяет проверку реального телефона/Poweramp.
