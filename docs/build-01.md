# Сборка, проверки и демо на build-01

По поручению владельца от 18 октября 2026 года выполнение сборки и демо вынесено с ноутбука на общую VM `build-01`, SSH `av@192.168.0.21`. Ноутбук редактирует и передает исходники; Node, компилятор, pytest и приложение выполняются на сервере. GitHub остается местом хранения кода и текущей проверенной процедуры релизной поставки. Эта настройка не регистрирует новый GitHub runner и не меняет чужие workflows.

## Выполнение

Из корня проекта:

```powershell
python dev/build01.py run
python dev/build01.py status
python dev/build01.py start-demo
```

`run` передает снимок текущих исходников, включая еще не закоммиченные изменения, проверяет SHA-256 архива и каждого файла, выполняет frontend build/test, собирает Docker-образ, запускает backend-тесты и только после успеха заменяет демо. Исходники читаются через `git ls-files`; `.git`, зависимости, приватные deployment-файлы, базы, ключи, `.env` и секреты не передаются. Не передаются и файлы пользовательской коллекции.

`start-demo` запускает уже проверенный образ без повторной сборки/тестов: проверяет успешный JUnit-отчет и метку SHA-256 образа. Можно указать `--snapshot <sha256>`. Это пригодно после остановки демо или временной ошибки его старта. Холодной инициализации на медленном диске отведено до пяти минут; установке образа до часа. Ошибка готовности не превращает прошедшие тесты в непроверенную сборку.

Рабочий каталог на сервере: `/home/av/build/phonoteka`. Снимки находятся в `sources/<sha256>`, результаты и полные логи - в `reports/<sha256>`, последний успешный запуск - в `current.json`. Контрольный файл `dev/snapshot.json` внутри снимка связывает исходный commit с хешами фактических файлов; commit сам по себе не означает отсутствие незакоммиченных изменений.

## Доступ к демо

Текущий стенд приемки доступен без SSH-туннеля: [Фонотека на build-01](https://phonoteka-build.st1.int.nd4y.icu/). Backend привязан к `192.168.0.21:18178`; внутренний HTTPS-прокси передает запросы на этот свободный порт. Ноутбук не выполняет приложение и не пересылает его трафик через SSH.

Для PWA и Secure-cookie используйте HTTPS-адрес. Прямой HTTP по LAN-IP не дает защищенного контекста service worker; кроме того, приложение проверяет Host. Не отключайте TLS, Secure-cookie или авторизацию ради тестирования.

Текущий экземпляр работает на проверенном GitHub-образе в контейнере с меткой `io.phonoteka.image_review`, с сохраненными синтетическими данными `browser-review/fixtures-v2`. Его состояние можно проверить без вывода переменных окружения и пароля:

```sh
ssh av@192.168.0.21 docker ps --filter label=io.phonoteka.image_review
curl --fail https://phonoteka-build.st1.int.nd4y.icu/health
```

Владелец - `owner`. Пароль хранится только на сервере в `/home/av/build/phonoteka/browser-review/fixtures-v2/owner_password` с правами `0600`; каталог имеет права `0700`. Получайте пароль только в своем SSH-терминале и вводите в форму входа. Не добавляйте его в Git, логи, отчеты или память. Это отдельная учетная запись стенда, не production.

Маршрут задается отдельным файлом `/volume1/docker/traefik-internal/dynamic/phonoteka-build.yml` на st1. Остальные правила прокси сохраняются; изменение этого файла не требует перезапуска прокси. Для отката удаляется только этот файл после сверки его содержимого. Само удаление маршрута не останавливает тестовый контейнер и не меняет данные.

### Прежний локальный dev-стенд

Команды `dev/build01.py start-demo` и `stop-demo` выше управляют прежним контейнером `phonoteka-demo`, его loopback-портом `8177` и каталогом `/home/av/build/phonoteka/demo`. Они не управляют текущим стендом приемки на `18178`. Не запускайте прежний dev-стенд для восстановления текущего: это другой экземпляр и другой набор состояния. `dev/tunnel.ps1` сохранен для совместимости; для текущего демо он не нужен.

Оба стенда используют синтетические WAV и CUE с тремя композициями, одна из которых намеренно недоступна для проверки навигации. Внешние провайдеры и inference выключены, реальная фонотека и production не подключены. Worker текущего стенда запускается отдельно только для контролируемой проверки задач; отсутствие worker означает, что новые задачи не выполняются. Файл прежнего стенда `demo/fail-detail-once` с ID синтетического трека вызывает одну ошибку получения его карточки для проверки сохранности черновика.

Доступность HTTPS не заменяет проверку установки PWA на физическом телефоне. Ручная приемка телефона и Poweramp отложена владельцем до конца разработки.

## Соседние задачи и ресурсы

- Выделенный BuildKit builder `phonoteka-build01` ограничен двумя CPU и 2 ГиБ RAM. Проверки идут последовательно; backend имеет два CPU/1,5 ГиБ, демо один CPU/512 МиБ. Builder останавливается после сборки, его кеш сохраняется.
- Файл `operation.lock` сериализует операции этого проекта. Если операция уже выполняется, новая завершается без остановки активной.
- Для медленного диска VM только установка системных пакетов временного dev-образа выполняется через `eatmydata`. Это исключает ненужные для одноразовой сборки fsync каждого пакета. В приложении/тестах нет глобального `LD_PRELOAD`, fsync файлов музыки и SQLite остается обычным; production Dockerfile не меняется этим преобразованием. При обрыве установки образ пересобирается. См. [описание пакета Debian](https://packages.debian.org/bookworm/eatmydata).
- Контейнер демо имеет имя `phonoteka-demo` и метку `io.phonoteka.dev=build01`. Контроллер отказывается заменять одноименный чужой контейнер.
- Нет глобального prune, удаления чужих образов/томов, перезапуска Docker и массовой остановки контейнеров. Разрешение владельца завершать существующие контейнеры не отменяет исключение для чужих активных сборок. Прочие сервисы сохраняются, пока их остановка не требуется.
- По первоначальному решению владельца от 20 октября ASR и нагрузочные проверки ждут освобождения ресурсов. Позднее разрешено увеличить CPU VM при наличии запаса st1 (CHG-036); RAM сохраняется. Текущая VM не поддерживает добавление CPU без остановки, поэтому увеличение не выполнено при активных общих сборках. Проверять нужно доступную RAM и давление I/O; свободный CPU сам по себе не означает, что сервер готов к тяжелой проверке.
- До/после операции сравниваются ID, время старта и restart count остальных контейнеров; изменения требуют разбора. Это обнаруживает изменения во время нашей операции, но само по себе не устанавливает их причину.

## Остановка, логи и откат

Следующие команды относятся только к прежнему dev-стенду `phonoteka-demo`:

```powershell
python dev/build01.py stop-demo
ssh av@192.168.0.21 docker logs --tail 100 phonoteka-demo
```

До успешной сборки и тестов старое демо остается доступным. При замене старый контейнер временно переименовывается и останавливается; если новое демо не проходит health, контроллер пытается вернуть старый контейнер. После успеха старый контейнер удаляется, его образ остается доступен. Данные демо сохраняются отдельно. Автоматического восстановления старой БД поверх новой нет; изменение схемы требует отдельного checkpoint/согласованного восстановления.

Если от прежнего dev-стенда остался SSH-туннель, завершать только его точно идентифицированный процесс. Не завершать чужие `ssh`, Node/Python или все процессы с одинаковым именем. Локальный прежний сервер останавливается только после подтверждения нового демо и сверки его PID/командной строки.
