# Измерения этапов обработки

Первый этап реализации P1 по [ТЗ v1.1](tracing-spec.md). Версия d7ecc70 установлена на st1 22.10.2026 после [полного GitHub CI](https://github.com/nd4y/phonoteka/actions/runs/39725975752):603 backend/170 frontend тестов,19ASR/7combined/15ordinary критериев и сверка62 установленных модулей. Пройденные проверки этого среза не означают полную приемку P1/P2.

Открыть: «Обработка» -> «Действия и события» -> «Ход обработки». На реальной партии подтверждены активные этапы,3 события SSE и измеренные длительности;10/10 и50/50 записей метаданных завершены с проверкой SHA резервной/рабочей версий и сохранности аудиопакетов. Отдельные интервалы могут оставаться неизвестными при потере записи telemetry; это явно неполная история, не ошибка или отмена самого файла. Для старых задач измерения задним числом не создаются.

В раскрытой карточке задачи появляется «Ход обработки»: текущие измеренные этапы, файлы, конкретные сервисы, elapsed, история с длительностями и HTTP-кодами. Ожидания нескольких источников показываются отдельно с безопасной причиной и retry_at. В новых результатах сохраняется срок по отдельному источнику; для старых используется имеющийся срок задачи без выдумывания истории.

Ответ исполнителя, счетчик полезной работы и свежесть браузерного snapshot различаются. Счетчики ответа HTTP/прочитанных байт обновляются только при фактическом событии, с ограничением частоты. Heartbeat и чтение API не двигают счетчик. Для недоступного внутреннего прогресса явно показывается отсутствие измерений. Предупреждения не инициируют отмену, повтор или перезапуск.

Существующие API /api/jobs/{id}/activity и SSE сохраняют owner auth. Добавлены server_now, executor_health, heartbeat_age_seconds, current_stages, stage_history, stages_truncated, provider_waits и provider_waits_truncated. Этап содержит непрозрачные stage/attempt/executor IDs, parent_stage_id, start/end, duration_ms либо null, elapsed, безопасный provider/HTTP status/reason, доступные progress_counter/unit/last_progress_age и предупреждения. Имя файла разрешается отдельно в авторизованной проекции из локального каталога, а не записывается в событие этапа.

Контекст распространяется в собственный ThreadPoolExecutor. Каждое вхождение файла получает attempt_id и каждый этап stage_id. Worker публикует activity_generation. Незавершенные этапы прежнего поколения/неактивного файла показываются как прерванные с неизвестной длительностью. Позднее завершение прежней попытки не скрывает текущую. Локальные длительности измеряются monotonic clock, интервалы после потери фактов не превращаются в завершенные нулевые.

## Границы первого этапа

- Подключены обычная файловая ветка worker и HTTP через Providers. Полные scan/album/export и внутренние checkpoint локального ASR требуют отдельного подключения и приемки.
- Используется существующий events: максимум10000 событий/сутки. Это ограниченная история, не журнал200000 этапов. UI возвращает последние100 этапов и первые100 ожиданий с признаками усечения. Полная история попыток/серверная пагинация еще не реализованы.
- Отдельная транзакция telemetry имеет SQLite busy timeout20мс; отказ записи не меняет исход музыкальной операции. После потери измерений выставляется history_partial, но независимый live snapshot при полном отказе БД еще не реализован. P1-08 полностью не принят.
- Полный P1-01..10, пределы P1-09 и браузерная/мобильная приемка не объявляются выполненными. SSR/unit-тесты не заменяют реальные UI проверки.
- OTLP SDK/exporter, trace_id/span_id, Collector/backend и Grafana относятся к P2 и пока не реализованы. Новый экран работает без них. Старым задачам измерения не добавляются задним числом.

Пороги: stale snapshot15с, heartbeat30/60с, soft записи60с, decode/fingerprint180с, подозрение на отсутствие измеряемого прогресса120с. Для ASR и HTTP нет придуманного общего deadline: пока бюджет не передан, нормальность длительности не утверждается. Предупреждения не меняют тайм-ауты и бюджеты обработки.

Проверки build-01 используют только исходники/generated данные и контейнеры1CPU/768МиБ. Перед поставкой выполнены GitHub-сборка, server postflight, fresh checkpoint и image-only update стека206; originalRO/schema2/private paths сохранены. Откат по действующему процессу с backup; изменение не добавляет схему БД и не меняет музыкальные файлы при чтении активности. Браузерная приемка по текущему указанию владельца не выполнялась.
