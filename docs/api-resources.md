# Именованные ресурсы API v1 и контекст Album Gain

Все маршруты имеют префикс `/api/v1`. Временные маршруты `/api` используют те же обработчики. Cookie-сессия требует Origin и CSRF для изменений; API-токен требует соответствующую область `jobs:write`. Сервер не принимает произвольные пути или команды.

## Предложения и ревизии

- `PATCH /proposals/{id}` принимает ту же модель, что создание предложения в карточке. `If-Match` содержит текущий SHA-256 рабочего файла. ID в URL должен быть последним предложением этой ревизии. Результат - новое предложение с новым ID; старое сохраняется. `base_proposal_id`, если передан, должен совпадать с URL. Поля закреплений, происхождения и служебные доказательства не принимаются от клиента.
- `POST /proposals/{id}/apply` принимает `{"acceptance_mode":"manual"}` или `automatic`, требует `If-Match` и `Idempotency-Key`, возвращает обычное задание с HTTP 202. Автоматический режим проходит общий quality gate; пустой или непроверенный пилот не позволяет применить предложение автоматически.
- `POST /revisions/{id}/rollback` принимает ID операции из `track.history[].id`. Для рабочей ревизии `If-Match` содержит текущий SHA-256 work; для `publish`/`rollback_ready` - текущий SHA-256 Ready. Требуется `Idempotency-Key`. Откат Ready доступен только владельцу и не меняет work. Наличие предыдущей версии и ее резервной копии проверяется обычным обработчиком задания.

Повтор принятого запроса с тем же ключом и телом возвращает исходное задание, включая повтор после изменения файла. Другое тело с тем же ключом возвращает конфликт.

## План публикации

1. `POST /publications/plan` принимает `track_ids` (1-200 разных ID), необязательный профиль `lyrics_required`, `instrumental` или `relaxed`, и `Idempotency-Key`. Профиль должен совпадать с текущим принятым решением каждого файла. Проверяются текущий аудит, приемка, рабочие байты, ожидаемая ревизия Ready и переносимость путей.
2. Ответ содержит неизменяемые `id`, `plan_sha256`, выбранные ревизии, снимки решений и исходного Ready, а также действия `add`/`replace`/`skip`. План не изменяет аудио.
3. `GET /publications/{id}` возвращает сохраненный снимок. Он не становится автоматически актуальным после изменений коллекции.
4. `POST /publications/{id}/commit` с `{"plan_sha256":"..."}` и новым `Idempotency-Key` повторно проверяет весь состав и ставит обычное bounded задание публикации. Измененный файл, приемка, профиль или Ready требуют нового плана.

Перед первым эффектом worker проверяет весь еще не выполненный состав. Перед каждым эффектом повторяются проверки конкретной ревизии, решения и ожидаемого Ready. Каждый файл имеет собственный журнал, резервную копию и восстановление; атомарность нескольких файлов не заявляется. После уже выполненных эффектов ошибка оставшегося файла дает частичный результат. Повтор принятого commit с прежним ключом возвращает прежнее задание.

Обычный `POST /jobs` с `kind=publish` также фиксирует исходное состояние Ready при постановке в очередь. Старое задание не может принять более новую публикацию за свой исходный файл.

## Album Gain

`replaygain_album` измеряет только явно выбранный список. Вызов из принятой сверки релиза передает `release_review_id` и `release_review_version`; группировка по одинаковому album-тегу не доказывает комплектность конкретного издания.

После измерения сервер сохраняет неизменяемую группу: ID участников, измеренные FileRevision, проверенные идентичности аудиопакетов и, при наличии, точную версию принятого релиза/подмножества. Кандидаты и предложения содержат ссылку `album_gain_group` в происхождении соответствующих полей.

Состав проверяется при выборе кандидата, постановке apply и непосредственно перед записью. Повторное измерение другой пересекающейся группы, замена аудио, исчезновение участника или изменение принятого подмножества инвалидируют старый Album Gain. Собственная проверенная запись только тегов сохраняет идентичность аудио и не мешает последовательному применению Album Gain к остальным участникам. Повторное внешнее распознавание не запускается.

`GET /album-gain-groups/{id}` возвращает состав и состояние `current`/`stale`. Старый контекст сохраняется для аудита. Ручной ввод численных ReplayGain-тегов остается ручным решением и не получает доказательство серверного измерения.

Проверки: `tests/test_api_facades.py`, `tests/test_album_gain_policy.py`. Результат полного прогона фиксируется в документах выпуска после запуска на build-01.
