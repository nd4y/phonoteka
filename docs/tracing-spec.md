# ТЗ: текущая активность Phonoteka, длительности этапов и подробные трассы

Версия 1.1, 21.10.2026. Статус: проект требований, только документы, без внедрения. Основание: CHG-039 в requirements-register.md и уточнение владельца: в первую очередь видеть, чем занято приложение, какие этапы долгие и где возможна потеря прогресса. Синхронизировано с [общим и инфраструктурным ТЗ v1.1](../../docs/observability/otlp-homelab-spec.md). Новые пороги, ресурсы и адреса являются проектными предложениями, не действующими настройками и не подтверждением реализации.

## 1. Результат для владельца

**Первая очередь P1 - текущая работа внутри Phonoteka.** На экране «Обработка» владелец видит активные задачи/файлы, текущий этап и исполнителя, сколько длится работа и когда был последний полезный прогресс, завершенные этапы, ожидания и причины, время следующей попытки и список «Требует внимания». Долгая полезная работа, возможное отсутствие прогресса, недоступность исполнителя и устаревшие сведения различимы. Для P1 не требуются Collector, trace_id или Grafana.

**Вторая очередь P2 - подробный разбор через OpenTelemetry/Grafana.** Из выбранной попытки или этапа открывается подробная трасса с вложенными операциями API/worker/inference и внешними запросами. P2 расширяет диагностику и принимается отдельно; ее отсутствие, сбой экспорта и истекший trace retention не отключают P1. Текущая активность берется из прикладного состояния и ограниченного журнала, а не из последнего экспортированного span.

Переход из файла к обработке и обратно сохраняет фильтры, выбранную запись и положение списка. Основная карточка называется «Этапы» или «Ход обработки»; «Подробная трасса в Grafana» - вторичная ссылка.

Успешная трассировка не означает успешного распознавания или записи тегов. При недоступности наблюдаемости обработка копии продолжает работать. Оригиналы, provider budgets, права источников, CAS, резервирование, отмена и проверки сохранности остаются обязательными.

## 2. Границы

P1 охватывает API, durable worker и inference: собственное состояние текущей работы, heartbeat исполнителя, измеряемые checkpoint, ограниченный журнал переходов, live UI/API, признаки задержек и фильтры. Сначала сверить и переиспользовать существующие job/attempt states, leases и SSE; наличие нужных механизмов в реализации не предполагается по одному документу. Бизнес-очередь не переписывается.

P2 добавляет SDK/OTLP export, JSON stdout correlation и Grafana-переходы. Существующие Prometheus-метрики и stdout не заменяются новым обязательным транспортом. Отключение tracing не отключает журнал/живой статус P1.

Инфраструктура P2 описана отдельно: [ТЗ v1.1](../../docs/observability/otlp-homelab-spec.md), разделы 3-12; требования P1 и их приемка - разделы 1.1-1.7 того же документа. Документ существует, инфраструктура по этой ссылке не объявляется развернутой. Чат: 01a15d54-fbac-7211-8833-33560b83b7cd. Развертывание не входит в этот этап проектирования.

Не входят: загрузка аудио в наблюдаемость, публичный trace viewer/status API, переписывание очереди, новые музыкальные провайдеры, браузерная запись действий пользователя, автоматическая приемка ASR и воспроизведение задним числом отсутствующих измерений. Порог задержки не дает разрешения автоматически kill/restart/retry: действующие отмена, budgets и recovery остаются самостоятельными механизмами.

## 3. Прикладная модель P1 и отображение в трассы P2

P1 связывает задачу, файл, попытку и конкретное вхождение этапа постоянными непрозрачными ID; время жизни прикладной попытки не ограничивается временем жизни span. Одна попытка может содержать несколько активных сегментов P2. Паузы и межпопыточное ожидание фиксируются прикладными переходами, без открытого многосуточного span. Ниже trace mapping применяется при включенной P2:

| Сущность | Представление |
| --- | --- |
| Запрос владельца | Короткий SERVER span API и операция создания/управления задачей |
| Задача | Постоянный job_id и связи с файлами; без открытого span на все часы/дни жизни задачи |
| Попытка файла | Новый корневой trace активного сегмента и INTERNAL span file.attempt с job_id, item_id и уникальным attempt_id; номер попытки хранится долговечно. Продолжение той же попытки - новый linked segment |
| Предыдущая попытка и постановка | Span Links на сохраненный контекст; bounded список ссылок, без разрастания всей истории в каждом span |
| Этап | Дочерний span с фиксированным именем из каталога; реальные параллельные этапы отображаются параллельно |
| HTTP провайдер | CLIENT span каждой фактически выполненной попытки; provider, безопасная операция, HTTP status, длительность |
| ASR RPC | CLIENT worker -> SERVER inference с W3C traceparent и внутренними decode/transcribe/align spans |
| Пауза, backoff, квота | Запись ожидания в журнале между попытками; новый trace после продолжения, ссылка на прежний trace |

Контекст API -> queued job -> worker сохраняется явно в разрешенном служебном поле БД, а не только в памяти процесса. Для записи, еще не имеющей track_id (scan), используется непрозрачный стабильный item_id, привязанный внутри приложения. Для CUE хранятся отдельные идентификаторы исходного образа, производной композиции и попытки, без пути в telemetry.

Контекст трассы хранится только при включенной P2 и необязателен для выполнения/показа P1. Инфраструктурное `file_id` соответствует прикладному `item_id`, не новой параллельной сущности; экспортировать единое `phonoteka.item.id`. Имена этапов прикладного каталога сохраняются как `phonoteka.stage`; canonical span names и allowlist mapping приведены в разделе 8.

ContextVar/context managers должны корректно передавать контекст asyncio, thread offload и вложенных задач, восстанавливать его в finally и исключать смешение файлов при конкуренции. Контекст inference извлекается только на доверенном аутентифицированном RPC. Внешние пользовательские trace-заголовки не задают sampling и бизнес-идентификаторы. К внешним музыкальным сервисам traceparent/tracestate/baggage приложения не отправляются.

## 4. Каталог этапов

| Группа | Этапы |
| --- | --- |
| Прием и аудит | discover, signature, stat, hash, probe, decode, integrity_check |
| Распознавание | fingerprint_sample, fingerprint_lookup, metadata_lookup, lyrics_lookup, artwork_lookup, youtube_lookup |
| Работа с результатом | candidate_evaluate, proposal_create, review_required |
| ASR | audio_prepare, inference_wait, transcribe, align, alignment_validate |
| Запись | preflight, backup, write_tags, reopen_verify, audio_identity_verify, commit |
| Производные | cue_extract, normalize, replaygain, publication, sidecars, rollback |

Для каждой операции определяется применимое подмножество. Не выполнявшийся этап не показывается как выполненный за 0 секунд. Cache hit и запрет provider policy записываются отдельно; HTTP span при отсутствии HTTP-запроса не создается. Кэш можно отобразить коротким lookup span с cache_hit=true. Проверка допуска провайдера фиксирует quota/rate-limit/breaker/policy решения с безопасным reason code.

No match, необходимость проверки и отмена являются исходами бизнеса, а не автоматически внутренними ошибками приложения. HTTP503 остается ошибкой конкретной внешней попытки; при запланированном повторе итог попытки файла deferred. Временная ошибка успешного retry не исчезает из истории.

## 5. Данные и время

Обязательные поля переходов журнала: job_id, item_id, attempt_id, attempt_number, stage_id, parent_stage_id, stage, started_at_utc, ended_at_utc или null, duration_ms или null, state, outcome, service, provider при наличии, reason_code и retry_at_utc при наличии. trace_id, span_id и telemetry_delivery_state необязательны для P1. Состояния этапа: running, succeeded, failed, cancelled, interrupted, deferred, skipped. У skipped обязательна причина; skip не используется для отсутствующего исторического измерения.

В snapshot/event также нужны server_now_utc, state_observed_at_utc, state_version/event_sequence, executor_instance_id/ownership_generation, last_heartbeat_at_utc, last_progress_at_utc или null, progress_kind/counter/unit, progress_observability, expected_deadline_at/retry_at при наличии, признаки activity_health с безопасными причинами/порогами и history_completeness. `stage_started_at_utc` snapshot соответствует started_at_utc текущего вхождения этапа. retry_at/retry_at_utc/next_retry_at означают одну серверную отметку, имя поля закрепить в OpenAPI, не хранить несколько независимых часов.

Три независимых измерения:

- execution_state: queued, running, waiting_provider, waiting_resource, retry_scheduled, paused, succeeded, failed, cancelled, interrupted. До реализации сопоставить с действующей state machine; подписи UI не требуют переписывать бизнес-состояния. Причины ожидания раскрывают deferred.
- activity_health: normal, long_running, no_progress_suspected, executor_unavailable, overdue_wait, unknown; признаки могут сочетаться и не переписывают подтвержденный исход операции.
- data_freshness: fresh, stale, unavailable; history_completeness: complete, partial, unmeasured. Состояние доставки P2 хранится отдельно. Потеря связи браузера не доказывает остановку worker.

Обновления привязаны к версии/поколению владельца попытки; поздний start/end/heartbeat старого процесса не оживляет и не завершает новую попытку. Terminal result не откатывается старым событием. SSE идемпотентен по sequence; gap требует нового snapshot. Poll/чтение snapshot не освежают last_progress/heartbeat. Reconcile после crash использует durable queue/lease, а не вывод «ошибка» по одному таймеру.

Ресурсы OTel для P2: service.namespace=phonoteka, service.name=phonoteka-api|phonoteka-worker|phonoteka-inference, service.version, deployment.environment.name=homelab, host.name=st1, service.instance.id. Прикладные атрибуты имеют префикс phonoteka.*: job.id, item.id, attempt.id, attempt.number, operation, stage, provider, outcome, reason_code, cache.hit. Стандартные HTTP-поля выбираются по зафиксированной версии semantic conventions, без смешения несовместимых версий. Идентификаторы непрозрачные, не содержат имя/путь или SHA содержимого.

UTC используется для сопоставления процессов, monotonic clock - для точной локальной длительности. Live elapsed рассчитывается из серверного elapsed/snapshot и клиентского monotonic таймера, только пока running подтвержден свежими данными. При stale/offline показывается последняя подтвержденная длительность и возраст сведений; дальнейшее время неизвестно. Reconnect сверяет snapshot, refresh не обнуляет таймер. Отрицательные интервалы/clock skew показываются явно. Доказанная потеря владельца дает interrupted/unknown_duration; одно отсутствие связи дает unknown/stale, без выдуманного времени окончания.

Раздельно отображаются очередь, выполнение, ожидание провайдера, пауза и итоговое wall time. Пересекающиеся дочерние spans не суммируются как общий elapsed. Время HTTP не объявляется временем работы самого внешнего сервера. Межпопыточное ожидание восстанавливается только по долговечным записям wait/resume; отсутствующие интервалы остаются неизвестными. ETA не вычисляется из суммы длительностей параллельных этапов и не обещается при неизвестном backoff.

### 5.1. Heartbeat, полезный прогресс и подозрительные задержки

Heartbeat подтверждает ответ исполнителя, checkpoint - продвижение конкретного этапа. Предложение: heartbeat <=10s, checkpoint не чаще одного в 5s или на естественных границах; отдельный живой heartbeat не доказывает продвижение блокирующего дочернего процесса. Источники checkpoint: bytes/единицы чтения/записи, доступные frames/chunks decode/fingerprint, ASR chunks без текста, отправка/ответ и deadline HTTP. CPU, TCP health и export spans не считаются полезным прогрессом файла. Для атомарной библиотеки без сигналов `progress_observability=unavailable`; проценты не придумываются, операция не повторяется ради измерения.

| Условие (проектный порог) | Отображение |
| --- | --- |
| Snapshot старше 15s при ожидаемом polling <=5s | «Данные устарели», без вывода об остановке исполнителя |
| Heartbeat старше 30s / 60s | «Нет свежего ответа исполнителя» / executor_unavailable, без автоматического business failed |
| Elapsed превысил soft threshold этапа | long_running, даже если полезный прогресс продолжается |
| Измеряемый checkpoint не меняется дольше stage progress threshold, heartbeat/snapshot свежие | no_progress_suspected с возрастом последнего прогресса и порогом, без утверждения доказанного зависания |
| Внутренний прогресс не наблюдается | «Прогресс внутри операции не измеряется», elapsed/deadline; без уверенного диагноза отсутствия прогресса |
| Ожидается ресурс, backoff до retry_at или ручная пауза | Штатное ожидание с причиной/сроком, не зависание |
| retry_at/deadline прошел более чем на 30s при свежих данных | overdue_wait с отдельной доступностью scheduler/worker; без нового автоматического retry |

Начальные soft thresholds, синхронные с общим ТЗ: read/write/verify 60s, decode/fingerprint 180s, сетевой запрос - фактический configured deadline +30s; provider backoff исключен. Измеряемый progress threshold первоначально 120s и уточняется по этапу. Для ASR/warmup/большого объема нужен бюджет по аудиодлительности, модели и объему; без бюджета показывать «норма не определена» и пользовательский фильтр длительности. Нельзя применять progress threshold к атомарной операции без checkpoint.

Это предупреждения UI, не timeouts исполнения. После >=50 сопоставимых завершенных измерений можно предложить soft warning=max(ручной нижний порог, 3*p95), разделяя provider/cache-hit/model и диапазон объема. В diagnostics показывать основание и действующий порог. Точная нормальность/зависание не выводится из одного elapsed. Никаких новых kill/restart/retry, внешних уведомлений или фоновых controllers этим проектом не создается.

## 6. UI и API

Экран «Обработка» - основной результат P1: сводка выполняемых файлов/ожиданий/пауз/проблем и раскрываемые карточки задач с отдельными параллельными работами. В строке файла видны попытка, этап, service/provider, elapsed, возраст последнего полезного прогресса, heartbeat и свежесть данных. «Нет активных задач» отличается от «нет свежих данных». Для waiting_provider обязательны конкретный сервис, причина, next_retry_at и обратный отсчет, если известны; для waiting_resource - ресурс. Если причин/провайдеров несколько, показывать их и следующие допустимые попытки, а не произвольно выбранного виновника.

Карточка файла «Этапы»/«Ход обработки»: список попыток, timeline завершенных и текущих этапов, длительности, безопасные причины и HTTP-коды. Процент/ETA только при реальном знаменателе; иначе объем работы и «общий объем неизвестен». «Требует внимания» различает долгое выполнение, отсутствие измеряемого прогресса, недоступность исполнителя, устаревшие сведения и просроченное ожидание. Цвет дополнен текстом/иконками. Нет измерений, partial history и unmeasured не подменяются успешным этапом за 0 секунд. Отсутствие trace_id не мешает карточке.

Отдельные состояния вторичной ссылки P2: интеграция выключена, трасса еще экспортируется, недоступно хранилище, истек retention, экспорт частично потерян. Они не меняют current activity и бизнес-исход. Наличие trace_id не дает зеленую отметку успеха.

Фильтры: активные/ожидание/требует внимания/завершенные, задача/файл/этап/provider/outcome/время, «дольше N секунд» и «без прогресса дольше N секунд». Сортировки - по возрасту последнего прогресса, длительности текущего этапа, началу; по умолчанию проблемные выше, затем активные. Пагинация на сервере <=100 записей страницы, стабильная сортировка/cursor. В существующем authenticated API - snapshot, попытки, этапы, provider/resource waits; конкретные маршруты закрепить в OpenAPI. Привычные названия файлов доступны только владельцу в UI/API, в telemetry имена/пути не экспортируются.

Live обновления - через существующий authenticated SSE с sequence/cursor и resnapshot после разрыва/gap; fallback polling <=5s. Целевой лаг переходов <=2s при SSE и <=7s на polling. Истекший owner session закрывает API/SSE. Соединение браузера и ответ исполнителя показываются раздельно. Текущий статус не запрашивается в Grafana/Jaeger/Tempo; завершенные spans могут появиться позже. Offline UI не изображает продолжающийся подтвержденный прогресс.

Вторичная кнопка «Подробная трасса в Grafana» строит ссылку по настроенному origin, datasource UID и валидному trace_id; параметры кодируются, произвольный redirect запрещен. При отсутствии интеграции доступны копирование имеющегося trace_id и пояснение, без блокировки P1. Back, refresh, мобильная компоновка и reduced-motion сохраняются. У старых задач явно «история этапов отсутствует»; измерения не восстанавливаются задним числом по mtime файлов.

## 7. Логи, метрики, безопасность

JSON stdout получает trace_id/span_id только из валидного активного контекста и attempt_id для корреляции. Существующий request_id сохраняется. События start/end/deferred/interrupted коррелируются с журналом, при рестарте trace recovery не создает ложный success. В Grafana должны быть переходы trace -> logs и log -> trace с учетом существующего VictoriaLogs, а не предположение о наличии Loki.

Запрещены: абсолютные/относительные пути, имена файлов, artist/title, тексты песен и ASR, аудио, полные URL/query, ключи, cookies, auth headers, содержимое ответов, произвольные exception messages. Для исключений по умолчанию отключить автоматическую запись exception/stack с данными; разрешить только тип и код из allowlist. Проверить FastAPI/HTTPX/ASR автоинструментацию на эти утечки; глобальное включение всего auto-instrumentation не допускается без проверки.

Высококардинальные job/item/attempt/trace IDs допустимы в закрытых traces/logs, запрещены как labels Prometheus. Новые агрегатные метрики: результат экспорта, потери/переполнение, длительности этапов, ожидание по провайдеру; имена/типы/labels фиксируются до реализации. Доступ к данным обработки сохраняет owner auth; истекший сеанс закрывает API/SSE. OTLP secrets и CA - отдельные protected files, не музыкальные provider keys.

P1 может добавлять агрегаты числа подозрительных этапов, stale executors и максимального возраста по ограниченному каталогу stage/service/reason, без item/attempt IDs. Heartbeat/checkpoint события не содержат аудио, текста ASR или пути. Внешние уведомления не входят в P1, предупреждения сначала отображаются в самом приложении.

## 8. Независимость P1, история и дополнительный экспорт P2

### 8.1. Прикладной журнал P1

Минимальный журнал и индекс попыток работают без SDK/Collector и не являются OTLP-outbox. Предварительная история: 14d завершенных попыток и <=200000 завершенных этапов. Дисковую квоту/размер записей и cleanup batches измерить до миграции; бюджет P1 не заимствуется у Badger P2. Активное краткое состояние хранится отдельно от подробной истории. Очистка не удаляет активные задачи, очередь, бизнес-результаты, музыку или backups.

При достижении бюджета ограничивается подробная история с partial marker, сохраняется bounded live snapshot. Если достоверного snapshot нет - unknown/stale, не старое «работает». Обновление секундомера не создает запись каждую секунду; журнал получает start/end/wait/resume и ограниченные осмысленные checkpoint. Нет длительного SQLite writer lock; сбой telemetry не вызывает повтор аудиооперации и не отменяет успешный бизнес-результат. Миграция совместима с очередями/schema и требует проверенного backup/rollback перед будущим внедрением.

История P1 14d и trace retention P2 7d независимы. После истечения trace TTL карточка этапов остается доступна с пояснением у ссылки. Tracing toggle управляет только P2.

### 8.2. Единый проектный контракт P2

OTLP HTTP/protobuf через background BatchSpanProcessor, compression=none. Предлагаемый trace endpoint `https://otlp.phonoteka.internal:4318/v1/traces`; base endpoint `https://otlp.phonoteka.internal:4318`, путь не добавляется дважды. Резервный gRPC `https://otlp.phonoteka.internal:4317` без HTTP-пути, listener по умолчанию выключен. Адреса - Docker aliases будущего Collector, не существующие подтвержденные endpoints.

TLS1.2+ с проверкой CA/hostname, mTLS и отдельный bearer из `/run/secrets/otlp_token`; CA `/run/secrets/otlp_ca.pem`, клиентские cert/key `/run/secrets/otlp_client.crt` и `/run/secrets/otlp_client.key`. Не использовать owner/metrics/ASR credentials, не хранить значения в Git/Env/logs. CA issue policy и identities еще требуют проверки. Insecure fallback/redirect с auth запрещены. Отсутствие конфигурации P2 не мешает startup/P1 и явно видно в diagnostics.

Для начальной обработки -100% прикладных файловых попыток при нормальном режиме, без sampling скрывающего ошибки/повторы. Частые health/metrics/SSE-poll запросы исключаются по отдельному правилу. Head sampling общего входящего запроса не должен случайно выключать прикладные traces. SDK API/SDK/exporter версии совместимы, зафиксированы dependency lock и образом, Python ABI проверен во всех3сервисах.

Согласованный между документами проектный профиль для проверки на build-01: SDK queue=2048 spans/process, batch<=128 spans, interval=1s, network timeout=2s, общий retry budget одного export<=5s с jitter, shutdown flush<=2s. Request<=512 KiB uncompressed с делением по bytes и числу spans, span<=8 KiB, <=32 attrs и значения<=256 UTF-8 bytes, <=8 events/links с <=8 attrs каждого. Один активный trace segment<=512 spans/1 MiB/15min; при достижении границы продолжить новым linked segment с тем же attempt_id, не отменяя/повторяя аудиооперацию. Новый бизнес-retry получает новый attempt_id. Если SDK не умеет нужные пределы, предложить проверяемый bounded adapter, не считать один batch count ограничением bytes.

Цели P2: дополнительный working set<=32 MiB/process в норме, краткий пик<=64 MiB, throughput падение<=5% и добавочная p95 latency рабочих операций<=5% на сопоставимом workload; исходные container/OOM limits не увеличиваются автоматически. Значения - бюджеты будущих испытаний, не полученные измерения. Export не блокирует event loop, очередь и retries конечны, потери/partial success наблюдаемы.

Предлагаемый backend - Jaeger2/Badger, Grafana datasource UID `homelab-traces-v1`; P2 retention=7d. Инфраструктурные ресурсы/квоты/readiness/rollback остаются в общем ТЗ и требуют собственной приемки. Trace visibility цель<=30s после конца сегмента не применяется к live status P1. Кнопку/реальный share URL и VictoriaLogs correlation проверить отдельно; проектный URL не подтверждает доставку.

Service/resource names из раздела 5 и `phonoteka.*` attrs согласуются с Collector allowlist: `phonoteka.job.id`, `phonoteka.item.id`, `phonoteka.attempt.id`, `phonoteka.attempt.number`, `phonoteka.operation`, `phonoteka.stage`, `phonoteka.provider`, `phonoteka.outcome`, `phonoteka.reason_code`, `phonoteka.cache.hit`. Snapshot health fields с временами не экспортируются автоматически целиком. Каталог этапов раздела 4 описывает прикладные операции; canonical spans: root `file.attempt`, чтение `audio.read`, декодирование `audio.decode`, fingerprint `fingerprint.compute`, провайдеры `provider.musicbrainz|lrclib|caa|shazam`, ASR `asr.transcribe`, запись `metadata.write`, проверка `result.verify`; остальные - `file.stage` с `phonoteka.stage` из ограниченного каталога. Никаких ID/путей в именах spans.

Журнал этапов не является полным OTLP-outbox. Падение процесса может потерять неэкспортированные spans; API сообщает этот предел. Дисковая очередь Collector защищает только принятые им данные и не восстанавливает потери SDK. Если требуется полное восстановление OTLP после сбоя приложения, это отдельное решение об outbox с оценкой нагрузки, а не обещание данного базового варианта. OTLP доставка может дублировать spans; неизменные IDs при transport retry, новая попытка обработки получает новый attempt/trace.

## 9. Раздельная приемка P1 и P2

### 9.1. Главный результат P1

Критерии P1-01..P1-10 ниже синхронизируются с разделом 1.7 общего ТЗ. P1 принимается с отсутствующей P2, без ожидания Collector/сертификатов/Grafana. Пороги раздела 5.1 являются предложениями для будущих проверок, не основаниями объявить приложение уже работоспособным.

| ID | Измеримый критерий |
| --- | --- |
| P1-01 | При полностью отсутствующих Collector/Grafana/OTLP config владелец видит все активные файлы, текущие этапы/исполнителей, время и очередь. Их работа и отображение не требуют trace_id |
| P1-02 | Последовательные/параллельные этапы и 2 одновременные задачи отражаются отдельными строками; timeline/длительности сверены с manifest, параллельные интервалы не суммируются как wall time. Лаг SSE <=2s, polling <=7s |
| P1-03 | Синтетический этап со свежим heartbeat и растущим checkpoint становится «долго» после порога, сохраняя признак прогресса; frozen checkpoint при живом heartbeat отдельно вызывает «возможно нет прогресса» в пределах threshold +7s |
| P1-04 | Зависший тестовый child при живом heartbeat не получает статус «все нормально»; child без доступных checkpoint честно показывает неизвестный прогресс и просроченный deadline/soft threshold. Диагноз не строится по CPU/экспорту spans |
| P1-05 | Потеря heartbeat вызывает stale/unavailable по 30/60s с допуском доставки <=7s; потеря браузерной сети вызывает stale UI, без ложного утверждения, что worker остановился. После reconnect - snapshot, без двойных/потерянных переходов |

| P1-07 | Crash/restart/новая ownership generation и запоздавший event старого worker не создают ложный running/success. Незавершенный интервал имеет unknown end/duration; перезагрузка страницы не обнуляет elapsed и не освежает heartbeat |

| P1-09 | На representative synthetic истории 200000 завершенных этапов и 100 отображаемых строк status/list API p95 <=300ms на стенде, снижение throughput обработки <=5% против того же workload без новых измерений; без длительного SQLite writer lock. Полный frontend показывает фильтры «долго»/«без прогресса» и объяснение признака |
| P1-10 | Owner auth API/SSE сохранен, имена музыки не экспортируются; неизвестные duration/progress/ETA не подменяются нулем/100%. Полностью выключенный tracing и истекший trace TTL не выключают живую карточку и предупреждения |

## 10. Этапы и передача инфраструктуре

1. P1: сверить реальные состояния/lease/API/SSE, доступность checkpoint и бюджеты/пороги; определить OpenAPI snapshot/events и совместимую миграцию журнала. Collector не prerequisite.
2. После отдельной команды на реализацию P1 - переходы/время/heartbeat/progress, UI «Обработка/Этапы», attention filters, bounded history и safe recovery. Обновить OpenAPI/справку без изменения музыкальных результатов и provider policy.
3. На build-01 принять P1-01..10 и применимые общие TR-регрессии с tracing off, включая реальный frontend по разрешенным правилам. Непроверенные критерии оставить открытыми.
4. После отдельного разрешения rollout P1: действующий процесс build/backup/совместимой поставки, сохранение коллекции и проверка live UI. Откат P1 - совместимые image/config/schema по заранее проверенному плану; отключение export не является откатом P1. Бизнес-БД не подменяется старой копией вслепую.
5. P2 независимо: проверить CA/auth/endpoints/квоты/версионные schema общего ТЗ, затем SDK/export/correlation и инфраструктурные проверки. Canary100% на ограниченном наборе, затем разрешенное включение и TR-01..12 в применимом объеме. При проблемах выключить только export/новый trace stack; P1 продолжает работу.

Открыто P1: соответствие исходникам существующей state machine/lease, конкретные routes и UI макет, quota/размер журнала, реальные checkpoint и ASR baseline, ownership recovery. Открыто P2: подтверждение предложенных endpoints/CA identities/backend resources, pinned SDK/Collector schema, byte-aware batching, runtime pressure guard, реальная Grafana/VictoriaLogs связность. Предложенный контракт между документами согласован по тексту, не проверен runtime. Отсутствие P2 не задерживает P1; отсутствие проверенного P1 UI не закрывается работающей Grafana.

Эта редакция выполняет только синхронизацию документов. Реализация, сборки, миграции, развертывание Collector и обновление production этим этапом не разрешены. Текущая обработка коллекции продолжается независимо от проектирования.
