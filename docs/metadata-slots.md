# Native artwork and lyric slots

ART-02, LYR-08 and format preservation in section 9 use an explicit native slot inventory. The owner can view all existing APIC/picture/covr objects and all USLT/SYLT/comment/MP4 lyric values. Language, description, native type, size and content fingerprint remain separate. MP4 does not have front/back picture types; its artwork items are shown as individual covr objects. Unknown or malformed pictures and unsupported lyric frames remain visible and read only.

`GET /api/tracks/{id}/slots` requires authentication, reads the current actual file and checks its full SHA-256 against the catalog revision. Responses are private/no-store. It returns at most 256 slots and at most 2 MiB of lyric preview characters across the response; a truncated slot cannot be loaded as a complete draft. Artwork preview is a separate authenticated/no-store endpoint. The browser renders lyric previews as text, never HTML.

An immutable proposal may contain `slot_selection: {inventory_sha256, cover_slot_id?, lyrics_slot_id?}`. Each slot ID fingerprints its native identity, occurrence and original content. The inventory fingerprint and full FileRevision must still match. The media writer checks selection before staging and independently checks preservation of every other native slot, encoded audio identity and the selected replacement after reopening. It does not replace every front cover or every lyric value. Multiple compatible slots without selection still fail closed. Legacy proposals with one compatible target remain compatible; the editor asks the owner to choose the target explicitly.

ID3 synchronized targets are supported SYLT frames with millisecond timestamps and lyric content type. Ordinary USLT values and unsupported SYLT formats are separate slots. The owner may load a USLT text into the editor and create a separate supported SYLT target; the original USLT is retained. No conversion silently merges languages. Choosing `new` creates a distinct synchronized target; a native description collision is a conflict. A new front cover is only allowed when there is no writable front target. This UI does not delete other slots. Ambiguous deletion or unsupported storage layouts abort before music replacement.

After selecting a non-first lyric target, the stored canonical LyricsDocument and subsequent scans of the same SHA retain that selected document. Native target identities are written into the prepared journal before the effect and recovered with it, so a crash before the database commit cannot silently select the first lyric instead. History keeps only the prior canonical native identity/text fingerprint; rollback reopens the restored bytes and materializes that exact prior document. Other languages remain in the media file. Known provenance of a retained first slot, including a read-only USLT, is kept under an independent native-slot reference, so selecting another slot cannot remove provider restrictions from a new export or backup.

The import control always previews before applying. UTF-8 is the initial profile, with optional BOM; Windows-1251, UTF-16 LE and UTF-16 BE require an explicit choice. There is no automatic charset guess. The preview has an explicit apply/cancel action and only then uses the existing LyricsDocument occurrence reconciliation, lock checks and undo stack. The 2 MiB and 20000-line parser limits apply. The browser sends the resulting Unicode draft through the existing proposal/document CAS path. No source encoding is written into an audio tag as if it were UTF-8 bytes.

Tests in `test_metadata_slots.py` use generated MP3, FLAC, MP4/AAC, Ogg/Vorbis, Opus, WAV and AIFF. They choose the second picture and lyric value, preserve other languages/images, verify encoded audio identity and reject missing/stale selections before journaling. Frontend encoding fixtures cover UTF-8 BOM, explicit Windows-1251, both UTF-16 byte orders and invalid/null/oversized input. These are software checks; physical Poweramp compatibility remains a separate acceptance requirement.

## Bounded artwork preparation

The owner upload accepts JPEG/PNG source images up to 20 MiB and 25 megapixels. `POST /api/tracks/{id}/artwork-preview` requires the owner session, CSRF, current FileRevision and explicit current cover-slot selection. This endpoint alone has a 29 MiB request envelope for base64 JSON; ordinary requests retain their previous 15 MiB limit. Output proposals retain the 10 MiB embedded-image ceiling, while the recommended default is JPEG, 1200 pixels on the larger side, 1.5 MiB and quality 88.

The owner can change output JPEG/PNG, 64..5000 pixel limit, 32 KiB..10 MiB byte budget and JPEG quality 40..95. The worker preserves aspect ratio, does not crop or upscale, applies EXIF orientation, removes image metadata and composites transparency on white for JPEG. It first reduces JPEG quality, then dimensions if necessary to meet the chosen byte budget. The UI shows source and result images, dimensions, MIME, bytes and SHA. Replacing the selected existing artwork with lower pixel area requires a separate owner confirmation. The accepted transform descriptor is retained in proposal/current metadata/history and restored with rollback.

Both upload transformation and native image validation use an isolated, single-admission decoder process. Source byte/pixel bounds, 512 MiB address-space and 8-second CPU limits on Linux plus a 10-second parent deadline bound decoding; stderr and arbitrary decoder text are not returned. Full pixel decoding is required, not only image-header verification. A malformed, animated, over-limit or resource-exhausting input returns an explicit error and does not modify music. The already pinned Pillow dependency is reused.

Validation descriptions are reused by SHA-256 in a process-local 512-entry LRU containing only hashes, MIME, bytes and dimensions. Neither raw images nor raw-byte cache keys are retained. A fair queue admits at most 32 waiting requests for up to 10 seconds while retaining exactly one decoder process. Equal-image validation waiters reuse the first completed result rather than starting another decoder or returning a false busy error during ordinary concurrent cover reads. Transform previews still run the selected transform profile; their output images are not cached here.

Preview records expire after 15 minutes and have a count cap of 100. Only hashes, dimensions, chosen profile/slot and source provenance are stored there, never either image. The preview receipt is server-bound to the current file, exact target and result hash; confirm/apply cannot substitute different bytes. Raw originals are not copied into settings or history. Source permission checks include derived-analysis/cache permission. A transformed provider image retains its original restrictions, and the derived byte fingerprint is registered to prevent a manual copy of the result from laundering that provenance. Explicit manual proposals without this new UI keep their existing authorized path and actual MIME/decode validation.

The selected cover remains canonical in the application after a second front-cover slot is replaced. Its full native/content fingerprint is retained in metadata and rollback history; the authenticated artwork endpoint explicitly selects it. Generic media callers retain their existing first-front default. Ready sidecar plans freeze both the accepted lyric slot and cover slot with native identity, native digest, content digest and the corresponding provenance. Actual native content is resolved against the frozen work SHA before sidecar effects and new exports. A review of the second lyric never authorizes exporting the first lyric under the second lyric's provenance. Plans predating explicit native source fingerprints require a fresh owner plan.
