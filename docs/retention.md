# Хранение rollback-версий и immutable exports

По умолчанию действует keep_all: приложение ничего не очищает автоматически. Оригинал, work и Ready не входят в очистку. История решений остаётся в БД после удаления допустимого backup; API явно показывает backup_pruned, возможность отката исчезает.

Владелец может задать возраст от 1 дня и число сохраняемых версий от 1. Последняя доступная rollback-версия защищена отдельно для work и Ready каждого файла. Полностью проверенный preview дополнительно сохраняет последнюю версию с совпадающим хешем. Пины владельца, queued/running/paused/interrupted/waiting задачи, текущий export, recovery и незавершённые публикационные intent блокируют удаление зависимых артефактов. Неизвестные каталоги, symlink, повреждённые backup/manifest и незарегистрированные файлы сохраняются для диагностики.

Web UI предоставляет предварительный список и настройки/pins владельца. Оно не удаляет файлы. Локальная проверка файлов в UI опирается на статические признаки; полная проверка SHA-256 и подтверждение всего отчёта выполняются оператором через CLI.

## Явная процедура оператора

Остановите только worker этого экземпляра и проверьте отсутствие выполняющихся операций. CLI получает те же state/work/publication/storage-guard и проверенную instance-конфигурацию, что worker. Второй scheduler или владелец storage domain не допускается.

    python -m phonoteka.retention preview --output /tmp/retention-plan.json

Прочитайте весь JSON: eligible-объекты, утрачиваемые rollback-версии, защищённые причины, byte counts, SHA-256. При keep_all=true eligible пуст. Для явного применения полной проверенной версии отчёта:

    python -m phonoteka.retention apply --plan /tmp/retention-plan.json --approval-token PLAN_HASH

PLAN_HASH берётся из plan_id конкретного отчёта. Это защита от случайного применения другого/изменённого плана, а не самостоятельное право доступа. Право обеспечивает локальный оператор с доступом к state и storage guard. План действует 15 минут после завершения preview. Изменение policy, pins, leases, задач, файлов или ссылок требует нового preview. CLI берёт scheduler/storage locks; окно создания новой ссылки закрывает SQLite BEGIN IMMEDIATE. Живые загрузки дополнительно держат shared OS lock, который очистка получает только exclusive/nonblocking.

До удаления создаётся fsync-журнал. При прерывании последующая очистка блокируется. Команда ниже сверяет результат, помечает действительно утраченные артефакты и не выполняет новых удалений:

    python -m phonoteka.retention reconcile

Неоднозначный результат остаётся конфликтом для оператора; оставшиеся файлы сохраняются. После успешной процедуры запустите worker этого экземпляра обычным способом. Эти команды не исполняются production автоматически при обновлении приложения.

## Доставка и leases

Клиент доставки с jobs:write вызывает POST /api/export-leases с export_id, получает lease ID на 30 минут и периодически вызывает POST /api/export-leases/{id}/renew. Завершённый POST /api/deliveries может передать lease_id; снимается только lease этого же клиента/сессии для этого поколения. Явная отмена: DELETE /api/export-leases/{id}. Отсутствие checksum остаётся лишь сообщением о копировании и не выдаётся за проверенную доставку.

HTTP-загрузка manifest, playlist и аудио автоматически удерживает shared lock на весь ответ, включая Range. Её TTL lease продлевается пока ответ активен. Даже после сбоя heartbeat/истечения TTL активный OS lock запрещает очистку. При завершении соединения lock освобождается. После аварии процесса его lock освобождает ОС; durable lease защищает поколение до TTL.

Для внешнего клиента, который не продлевает leases, закрепите export на время долгой передачи. FolderSync, читающий обычный Ready через SMB, не затрагивается этой очисткой: Ready никогда не удаляется автоматически.
