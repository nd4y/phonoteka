# Переход схемы состояния

Новый экземпляр создает схему 2. Существующая схема 1 не изменяется при старте app/worker: процесс завершает запуск с конкретной командой миграции. Production app и worker обновляются одной версией. Перед переходом оператор останавливает оба компонента; открытая вкладка браузера не является подтверждением остановки API.

В одноразовом контейнере нового образа с теми же state, storage guard и конфигурацией:

```sh
python -m phonoteka.migrations status
python -m phonoteka.migrations migrate --confirm-stopped
```

Runner удерживает общий scheduler lock и storage writer lock. Работающий worker блокирует миграцию. Флаг подтверждает, что оператор также остановил API; lock приложения не управляет независимым редактором SQLite. Параллельное изменение состояния между checkpoint и DDL обнаруживается через `data_version` и прерывает переход.

Перед DDL создается `/state/migrations/<UUID>/checkpoint.sqlite3` с проверенным manifest, размером, SHA-256 и `quick_check`. Provider policy проверяется до резервирования: известный запрет копирования не обходится. Сырой provider cache, активные сессии и API credentials исключаются из копии; запрещенное содержимое предложений очищается с сохранением происхождения. Это совместимый checkpoint состояния, а не копия музыкальной коллекции.

Manifest также перечисляет существующие backup/export/retention artifacts: относительный путь, размер, SHA-256 и исходный state root. Содержимое этих blobs не копируется. В реестре сохраняется независимая ссылка `maintenance_artifact_refs:<UUID>`; retention защищает связанные history/export объекты даже после снятия обычного owner pin. Поэтому checkpoint зависит от сохранности исходного state и не является переносимой полной резервной копией. Для переносимой копии остается отдельная штатная процедура backup.

DDL выполняется одной транзакцией. Последними проверяются ledger, write barriers и целостность, затем меняется `user_version`. Сбой до commit откатывает схему к 1; checkpoint и исходные blobs сохраняются. Сбой после commit или синхронизации не объявляется успешным: marker блокирует обычные подключения до явной сверки.

```sh
python -m phonoteka.migrations status
python -m phonoteka.migrations verify-checkpoint /state/migrations/<UUID>
python -m phonoteka.migrations migrate --confirm-stopped --retry
```

`--retry` не переписывает музыку. Для уже зафиксированной схемы 2 он проверяет ledger, barriers, БД и checkpoint и завершает учет; для оставшейся схемы 1 выполняет новый проверенный переход. Причина сбоя в marker ограничена типом исключения; секреты и полный stderr туда не попадают.

Каждое обычное подключение проверяет поддерживаемую версию. INSERT/UPDATE/DELETE каждой application table дополнительно защищены SQLite triggers с функцией версии, зарегистрированной новым `db.connect`. Подключение старого процесса без этой функции не может записывать схему 2. Это технический барьер от неосведомленного legacy writer, а не защита от оператора, сознательно удаляющего triggers или меняющего БД через сторонние инструменты. Миграция не обещает остановить уже исполнявшуюся файловую операцию: именно поэтому worker сначала останавливают, а runner захватывает его locks.

Восстановление совместимого checkpoint создается только в **новом пустом каталоге**:

```sh
python -m phonoteka.migrations restore-checkpoint /state/migrations/<UUID> /restore/state --confirm-stopped
```

Результат имеет схему 1, отозванные credentials, новый auth epoch, выключенные расписание/webhook и recovery mode. Он требует совместимого образа либо нового явного перехода к схеме 2. Backup blobs остаются по исходным путям; их наличие и хеши проверяются до восстановления. Work и Ready не копируются и не откатываются. После подключения восстановленного состояния выполняют штатную сверку фактических ревизий и только затем отдельное `acknowledge-recovery`. Существующий state каталог этой командой не заменяется.

В синтетическом `dev/demo.py` разрешен отдельный переход после остановки прежнего demo-контейнера. Он не используется production entry point и не монтирует личную коллекцию.

## Совместимые расширения схемы 2

Базовый SQL схемы 2 и его контрольная сумма неизменны после выпуска.
Таблица trace_attempts добавляется при запуске отдельной транзакцией
вместе с INSERT/UPDATE/DELETE barriers. Перед этим проверяется прежний
ledger и полнота существующих barriers. Ledger и user_version не меняются;
ошибка до commit оставляет исходную схему. Проверка не исправляет
поврежденный ledger или отсутствующие triggers автоматически.

Совместимый образ схемы 2 до внедрения трассировки может открыть эту БД
после отката: добавочная таблица не меняет его контракт и также защищена
барьерами. Регрессия фиксирует checksum ранее установленного ff62cf4d,
проверяет запуск API со старой БД, идемпотентность и транзакционный откат.
