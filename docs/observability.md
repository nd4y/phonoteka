# Метрики, stdout и Grafana

Все три контейнера запускаются со структурированными JSON-логами в stdout. Одна строка соответствует событию; поля: timestamp UTC, level, service, version, event, request_id, job_id, track_id, kind, state, provider, code, duration_seconds. Отсутствующие поля не добавляются. Request ID генерируется сервером и возвращается в X-Request-ID. LOG_LEVEL=DEBUG|INFO|WARNING|ERROR|CRITICAL, по умолчанию INFO. Docker уже ограничивает журнал тремя файлами по 10 МиБ.

Журналируются запуск/остановка, HTTP с шаблоном маршрута, начало/результат задания и попытки файла, пауза/ожидание источника, операции провайдеров, ASR и загрузка модели. Пароли, токены, заголовки, IP клиента, параметры запроса, пути аудио, музыкальные теги, текст песни и сообщения исключений в stdout не попадают. Для исключений остаются тип и кадры стека без значений локальных переменных. Небезопасный access log Uvicorn выключен; сообщения сторонних библиотек не переносятся в журнал целиком. Аудит изменений в SQLite остается отдельным журналом.

Создайте отдельный случайный scrape-токен длиной не менее 24 символов в защищенном файле. METRICS_TOKEN_FILE в .env указывает его **путь на хосте**; compose монтирует его во все три сервиса как /run/secrets/metrics_token. Не используйте пароль владельца или ASR-ключ. Вызовы метрик требуют Authorization: Bearer с этим токеном; сессия владельца и API-токен доступа к коллекции его не заменяют.

- GET /metrics: процесс API и агрегаты каталога/очередей/провайдеров из SQLite.
- GET /metrics/worker: фиксированный внутренний proxy к worker:9000/metrics.
- GET /metrics/inference: фиксированный внутренний proxy к inference:8001/metrics.

Endpoint worker не публикуется на хосте. ASR и worker остаются в своей Docker-сети. Proxy не принимает произвольные URL и не следует перенаправлениям. Каждый scrape возвращает только метрики соответствующего компонента. Ошибка компонента дает HTTP503, а не ложный успешный пустой scrape.

Сборщик читает SQLite в read-only/query-only транзакции с таймаутом 0,3с и кешем 5с; не обращается к музыкальным файлам или провайдерам. phonoteka_collector_up=0 и collector_last_success_timestamp_seconds показывают недостоверный/устаревший снимок. Сохраненные очереди, состояния файлов, лимиты и кеш доступны сразу после перезапуска. HTTP, счетчики попыток и гистограммы живут в процессе и сбрасываются при перезапуске; Prometheus rate/increase учитывает сброс. Состояния job_items и число запросов за скользящие24ч - gauges, к ним нельзя применять rate/increase. Не используйте ID файлов/заданий или URL как labels.

## Scrape-конфигурация

monitoring/prometheus.example.yml содержит три scrape job с app=phonoteka, instance и service. Укажите адрес API и отдельный токен через authorization.credentials_file; файл читается процессом Prometheus/vmagent. На существующем сервере допустима credentials в закрытом конфиге, если нет отдельного secret mount. Не сохраняйте значение токена в репозиторий. Рекомендуемые scrape_interval30s и scrape_timeout10s. Не отключайте проверку TLS для HTTPS-доступа.

## Дашборд

Импортируйте monitoring/phonoteka-dashboard.json в Grafana. Источники DS_METRICS (Prometheus-compatible) и DS_LOGS (VictoriaLogs) выбираются в переменных. Фильтры экземпляра, компонента, этапа, провайдера; поиск логов по Job ID и Request ID. monitoring/build_dashboard.py воспроизводит JSON без сетевых обращений.

Разделы: состояние сервиса, очереди/скорость/повторы/P95, провайдеры/бюджет/кеш, форматы/результаты/YouTube, ASR, HTTP, ресурсы процессов, достоверность SQLite и логи stdout. CPU/RSS относятся к Python-процессу, не включают дочерние ffmpeg/yt-dlp и память всего контейнера. Модель ASR загружается лениво, поэтому model_loaded=0 до первого задания нормально. Пустая гистограмма означает отсутствие новых выполнений; дашборд не создает искусственных ошибок и не запускает аудиозадания ради графика. Установка дашборда не включает внешние уведомления.
