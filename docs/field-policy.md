# Закрепление значений и приоритеты источников

В карточке файла блок «Закрепленные поля» защищает уже встроенное значение от последующих предложений. Сначала сохраните и примените ручную правку, затем закрепите ее. Допускается закрепить пустое поле: поиск не заполнит его без нового решения владельца. Для замены защищенного значения снимите закрепление и сохраните это решение.

Поддержаны все записываемые текстовые поля, MusicBrainz ID, Track/Album ReplayGain, front cover и текст. Многозначный тег защищается целиком, включая второе и последующие значения. Обложка закрепляется по SHA-256 реального изображения. Текст закрепляется целиком, вместе со словами и таймкодами; раздельные locks слов и времени относятся к более подробной модели LyricsDocument и не заявляются этой функцией.

Закрепление связано с ID физической копии, полным хешем файла и хешем значения. После изменения других тегов оно продолжает защищать то же значение. Если закрепленное поле уже изменилось, появляется конфликт: запись блокируется до решения владельца. Сначала снимите старое закрепление; повторное закрепление фиксирует проверенное текущее значение. История другой физической копии не переносится по совпадению аудио.

Выбор кандидатов не заменяет закрепленные поля: остальные выбранные значения формируют предложение, а исключенные поля отмечаются в `field_policy.blocked_fields`. Ручное предложение с изменением защищенного значения получает `409 field_locked`. Старое предложение, созданное до закрепления, также проверяется при создании задания и непосредственно worker перед записью.

В настройках «Приоритеты источников» задается порядок отдельно для каждого поля. Он разрешает пересечение значений из выбранных владельцем кандидатов: например, название записи из MusicBrainz, альбом из выбранного Discogs-релиза. Закрепления владельца имеют приоритет всегда. Настройка не включает отключенные интеграции, не определяет права использования данных и не включает автоматическую запись. Для каждого выбранного поля сохраняются кандидат/провайдер, время получения, хеш ответа и причина выбора. Изменение приоритетов не переписывает уже созданное предложение или музыку.

API:

- `GET /api/tracks/{id}/policy` возвращает поля, закрепления, текущий SHA, версию и `stale_fields`.
- `PUT /api/tracks/{id}/policy`: owner session + CSRF + `If-Match` с текущим SHA; JSON `{"fields":["title","cover"],"base_version":0}`. Полный список заменяет прежний набор. Несовпадение SHA/версии дает `412`.
- `GET/PUT /api/policies/sources`: только owner session. PUT принимает `{"priorities":{"album":["discogs","musicbrainz"]},"base_version":0}`. Отсутствующие поля используют начальный порядок. Пустой объект возвращает все порядки по умолчанию.
- Обычные scoped API-токены могут читать политику трека при `read`, но не меняют решения владельца или глобальные приоритеты.

Изменение закреплений при queued/running/paused/interrupted apply/rollback того же файла получает `409 track_mutation_pending`: дождитесь согласованного завершения или отмены. Это исключает смену policy между допуском задания и атомарной заменой.

Хранение использует versioned keys в `settings`, без изменения schema1. Для защиты нужны согласованные новые app **и worker**: старый worker не реализует проверку locks. Обновление выполняется после безопасной паузы на границе файла и проверенного checkpoint. Откат старого образа сохраняет данные policy в БД, но не обеспечивает новые запреты; их нельзя оставлять доступными в UI как работающие при старом worker.

Проверки находятся в [test_field_policy.py](../tests/test_field_policy.py). Их наличие не означает запуск: результаты текущего удаленного прогона фиксируются отдельным CHECK в [реестре](requirements-register.md).
