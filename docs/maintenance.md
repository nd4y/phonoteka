# Backup, восстановление и обслуживание

Эти команды выполняет администратор с доступом к volumes. Они не открывают публичный recovery endpoint. Перед backup остановите **worker этого экземпляра**, дождитесь безопасного завершения операций и проверьте отсутствие `running`/неразобранных `interrupted` заданий. Общие scheduler/storage locks не дадут запустить обслуживание рядом с работающим writer. App может оставаться доступным для чтения; новые задания будут ожидать остановленный worker.

Смонтируйте отдельный каталог для backup. Назначение должно отсутствовать и лежать вне original/work/Ready/state:

```sh
python -m phonoteka.maintenance backup /backups/state-20261018
python -m phonoteka.maintenance verify /backups/state-20261018
```

Backup использует SQLite Online Backup API, переводит копию БД в самостоятельный журнал DELETE, копирует версии rollback и неизменяемые экспорты, проверяет SHA каждого артефакта и `quick_check`, затем атомарно фиксирует каталог. Кеш источников, активные сессии и API-токены исключаются. В БД остается хеш пароля владельца: каталог имеет приватные права и должен храниться как защищенный backup. Музыкальные деревья и secret-файлы **не включены**. Для восстановления после отказа NAS нужен отдельный backup музыки и секретов на другом устройстве.

Восстанавливайте только в новый каталог и отдельный изолированный stack, с прежним mapping `/work`, `/publication`, `/state`, совместимыми образами и отдельной копией secret-файлов:

```sh
python -m phonoteka.maintenance restore /backups/state-20261018 /restore/new-state
```

Процедура не перезаписывает существующее state. Проверяются все заявленные артефакты, повышается auth epoch, отзываются сессии/API-токены, выключается расписание и отменяется старая очередь. Включается `recovery_required`: доступны только сканирование/аудит. Старый snapshot БД не откатывает музыку. При несовпадении файлов сверяйте историю и фактические ревизии; не подменяйте новые файлы старыми автоматически.

После проверки восстановления и сопоставления work/Ready остановите worker и выполните явное административное завершение:

```sh
python -m phonoteka.maintenance acknowledge-recovery
```

Команда сверяет SHA всех текущих каталогизированных work-файлов и опубликованных ревизий. Пропуски и несовпадения блокируют выход. Старая очередь/расписание не включаются; новые действия требуют новых заданий. Для штатного повторного запуска также должны быть корректны mount attestation и флаги записи.

Версии rollback и Ready-export по умолчанию сохраняются полностью. Автоматическое удаление музыки и версий восстановления отсутствует. Кеш ограничен временем/размером, события ограничены 24 часами и 10000 записями. Для оставшегося после аварии scratch есть отдельная двухфазная операция:

```sh
python -m phonoteka.maintenance prune-staging --older-than-days 7
python -m phonoteka.maintenance prune-staging --older-than-days 7 --apply
```

Первая команда выводит кандидатов, вторая повторно проверяет их под блокировками. Разрешены только каталоги `cue-*`/`normalize-*` внутри `.phonoteka-staging`, без symlink и старше grace period. Неразобранное прерывание блокирует очистку. Финальные `.phonoteka-derived`, оригиналы, Ready, backups и exports не удаляются. При нехватке места новые операции завершаются явной ошибкой, не освобождая место за счет rollback.

Настройки показывают доступное место, кеш и последний backup встроенной процедуры. `/api/reports/operations` возвращает приватный диагностический JSON без имен треков, полных путей, текста и секретов. Внешний checkpoint развертывания не выдается за встроенный backup и не появится в этом поле автоматически.
