# Трассы обработки и HTTP/DNS

Цепочка: API → долговечная задача → отдельный trace попытки трека → этапы → HTTP → resolver/TCP/TLS/отправка/получение. `job_id`, `item_id`, уникальный `attempt_id` и номер попытки доступны в attributes. Между созданием задачи, повторными попытками и RPC inference сохраняются связи. Законченные до включения tracing задачи не получают искусственных измерений.

## Просмотр

В «Обработка → задача → Ход обработки → Измеренные этапы» ссылка **Подробная трасса в Grafana** открывает waterfall выбранной попытки. В Grafana есть отдельный дашборд `phonoteka-tracing`, поиск по компоненту и тегам. Для поиска файла: `phonoteka.item.id=UUID`; задачи: `phonoteka.job.id=UUID`. Имена файлов остаются в авторизованной Фонотеке; в Grafana используются непрозрачные ID. На родительском span можно раскрыть вложенные операции.

`http.client` измеряет обмен до чтения/закрытия тела ответа, включая ожидание клиента. Внутри отдельно видны TCP, TLS, отправка заголовков/тела и получение заголовков/тела, когда HTTPX/httpcore действительно выполняет их. Есть метод, имя сервера, безопасный шаблон известного endpoint и HTTP-код. Полные URL, query, заголовки и содержимое ответа не записываются. Повторные HTTP-попытки являются отдельными spans. Cache hit не создает выдуманного HTTP.

`dns.lookup` измеряет вызов системного resolver (`getaddrinfo`), его имя и число результатов. Это не захват DNS-пакетов: кеш ОС может ответить без сетевого запроса. При повторном использовании соединения вызова resolver может не быть. Не следует считать отсутствие DNS/TLS-span ошибкой или время HTTP временем работы внешнего сервера. Параллельные дочерние длительности не суммируются как wall time.

ShazamIO использует aiohttp: его `http.client` заканчивается при получении заголовков (`phonoteka.operation=response_headers`); последующее чтение тела не включено. Вызовы сторонних процессов, например yt-dlp, не перехватываются как отдельные HTTP-запросы; их общая операция остается в прикладных этапах.

## Конфигурация

Tracing включается только `PHONOTEKA_TRACING_ENABLED=true`. Профиль отдельного Collector/Jaeger: `monitoring/tracing/`; пример наложения на приложение: `compose.tracing.yaml`. Развертывание на st1 выполняется через Portainer с сохранением действующих путей, образов и Env. Не применять пример поверх production вслепую.

`OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` - полный HTTPS endpoint, ровно `/v1/traces`. Отдельные файлы: CA, клиентские сертификат/ключ и bearer. Не использовать owner/ASR/metrics credentials; нет insecure fallback, auth-redirect или доставки контекста музыкальным провайдерам. Внешние trace-заголовки API игнорируются; inference извлекает контекст только после штатной RPC-аутентификации. Секреты генерируются на NAS и не передаются build-01.

`GRAFANA_TRACE_ORIGIN` - HTTPS origin без пути/credentials; `GRAFANA_TRACES_DATASOURCE_UID` - UID существующего Jaeger datasource. Генератор дашборда принимает тот же UID через environment. Просмотр через Grafana сохраняет ее аутентификацию. Collector/Jaeger не публикуют порты на хост и не получают публичного маршрута.

Состояние API export: авторизованный `GET /api/diagnostics/tracing`. Все процессы также отдают `phonoteka_tracing_{accepted,exported,dropped,failed,partial}_spans_total` и gauges `queued`, `queued_bytes`. Счетчики относятся к текущему процессу и сбрасываются при рестарте. `exported` означает принятие следующим узлом, а не гарантированную бессрочную сохранность. Подробные попытки по-прежнему видны в прикладном журнале при отключенном tracing.

## Пределы и отказ

Очередь процесса ограничена8МиБ: на каждый ожидающий span заранее резервируется его максимальный допустимый размер8КиБ, поэтому одновременно ожидают не более1024 spans. Gauge `queued_bytes` показывает этот резерв, а не фактический размер сериализованных данных. Кодирование выполняется один раз в отдельном потоке экспорта; слишком большой span отбрасывается до отправки. `accepted` означает принятие в ограниченную очередь, последующий отказ кодирования учитывается в `dropped`. Атрибуты ограничены32/256 символами, events/links -8. Batch ≤128 spans и менее512КиБ, интервал1с, конечный сетевой timeout. При отказе очередь ограничена, потери считаются, нет повторного выполнения аудио. Остановка flush ограничена2с; crash может потерять непринятые spans. Collector использует постоянную byte-sized очередь256МиБ с файлом≤4ГиБ и конечными retry. OTLP-вход проверяет mTLS+bearer, лимит512КиБ, отвергает compression; второй allowlist удаляет неразрешенные поля.

Для попытки новый связанный сегмент начинается после 128 spans (при лимите 8 КиБ на span - не более 1 МиБ закодированных spans) или после 15 минут. Планировщик завершает и продолжает все открытые этапы с тем же attempt_id, сохраняя вложенность и Link на предыдущий интервал. Аудиооперация продолжает выполняться ровно один раз. У каждого интервала собственный span_id; завершение одного сегмента не означает завершение всей операции. Временные границы соседних интервалов совпадают, итоговый результат записывается в последний. Полная длительность также сохраняется в журнале этапов. Более128 одновременно открытых spans не создаются; лишние измерения учитываются как потери. При задержке планировщика экспорт может произойти позже дедлайна, но timestamp конца ограничен. После приостановки процесса дольше целого сегмента непокрытый интервал явно отмечается `scheduler_delay`, вместо генерации неограниченного числа вымышленных сегментов. При выходе из попытки дедлайн отменяется, повторное завершение span безопасно.

Jaeger single-node Badger хранит данные на NVMe с TTL7дней. Это отсутствие HA; trace retention не является backup коллекции. Прикладные результаты, очередь и резервные версии музыки находятся отдельно. Контроль ресурсов SDK/Collector не заменяет лимиты контейнера или измерение нагрузки на общем сервере.

Дедлайны активных попыток обслуживает один daemon-планировщик на процесс. Для каждой попытки не создается отдельный поток: этот вариант превысил согласованный бюджет пропускной способности в GitHub и на build-01. Отмененный дедлайн освобождает ссылку на состояние попытки; планировщик удаляет отмененные записи из очереди.

Для встроенного поиска Grafana 13 используется Jaeger 2.20: начиная с Jaeger 2.21 прежний endpoint поиска, используемый этим datasource, отсутствует. TTL не является жесткой дисковой квотой. На st1 каталог `${TRACE_ROOT}/jaeger-bounded` - отдельный Btrfs subvolume с лимитом referenced bytes32ГиБ. Применение проверено отказом записи `EDQUOT` на временном лимите16МиБ и чтением итогового max_rfer34359738368. После остановки только trace-стека через Portainer скопированы и сверены все6файлов БД; прежний `${TRACE_ROOT}/jaeger-v220` сохранен для отката. Лимит общего appdata не менялся. В других окружениях наличие каталога само по себе не создает квоту: ее нужно отдельно настроить и проверить до включения producers.

Выделенный корневой сертификат действует пять лет, серверный и клиентский - один год. До истечения следует проверить сроки и подготовить замену всей цепочки с проверкой строгой валидации, затем обновить только ingress и клиента и проверить доставку контрольной трассы. Файловые bind mounts удерживают inode: простая замена файла через rename не обновляет содержимое уже смонтированного файла; требуется управляемое пересоздание контейнера либо безопасное обновление содержимого с сохранением inode. Предыдущие сертификаты сохраняются в защищенной резервной точке до проверки отката. Секреты не передаются в Grafana и не включаются в логи.

Откат: вернуть сохраненные app/inference image IDs и compose/Env через Portainer либо выключить export (`PHONOTEKA_TRACING_ENABLED=false`). Дополнительная таблица `trace_attempts` совместима со старым приложением; не восстанавливать старую бизнес-БД поверх новых результатов. Trace-стек можно остановить отдельно после отключения producers; его данные сохраняются.
